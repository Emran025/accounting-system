# معمارية تجربة Marketplace الإدارية

**الحالة:** تصميم تنفيذ معتمد داخلياً.  
**النطاق:** تجربة المؤسسة داخل Accore. لا يتضمن هذا المستند صفحة Marketplace العامة أو Checkout أو الدفع.  
**الهدف:** جعل إدارة الكتالوج والعروض والطلبات مساحة عمل تشغيلية واضحة ومرئية، لا صفحة CRUD مركبة.

## 1. حكم التدقيق على الواجهة الحالية

الواجهة الحالية سليمة وظيفياً من حيث الجلب والصلاحيات والنشر والتحويل، إلا أن بنيتها تعطي العناصر التشغيلية المتباينة الوزن نفسه: تبويبات قصيرة فوق جدول أو بطاقات، وحوارات إدخال عامة. لا تظهر وسائط المنتج كأصل له دورة حياة، ولا تُرى نتيجة العرض قبل نشره، ولا تمنح قائمة الطلبات سياقاً كافياً عن العميل والبنود والنشاط والتحويل. لذلك فهي لا تحقق معيار لوحة تشغيل احترافية.

| الفجوة | أثرها على المستخدم | المعالجة المعتمدة |
|---|---|---|
| صفحة واحدة بستة تبويبات متساوية | انتقال ذهني متكرر وغياب أولوية العمل | أربع مساحات عمل محددة: موجز، مكتب الطلبات، استوديو الكتالوج، استوديو العروض؛ وتبقى الصحة التشغيلية مساراً ثانوياً |
| حقل رابط غلاف واحد | لا توجد مكتبة أو معاينة أو ترتيب أو نص بديل | مكتبة أصول عامة + معرض متعدد الأصول + أدوار للوسائط + معاينة |
| العرض نموذج حقول | لا يمكن رؤية هدف العرض ومنفعته ونافذته بصورة تسويقية | باني عرض متعدد المراحل مع قائمة المنتجات المستهدفة وبطاقة معاينة |
| الطلب صف جدول فقط | يضيع سياق العميل والتحويل والنشاط | مكتب طلبات: قائمة قابلة للفرز + لوحة تفاصيل جانبية + خط زمني + إجراءات مرشدة |
| تحليل مبعثر | لا يقود المستخدم إلى قرار | موجز من 4 مؤشرات وقمع واحد وقائمة عناصر تحتاج انتباهاً |

## 2. المبادئ التصميمية

> **الصفحة الواحدة يجب أن تجيب عن سؤال تشغيلي واحد.** لا تحوّل الشاشة إلى لوحة لكل شيء.

تستعمل الواجهة حالة هادئة من السطوح البيضاء والحدود الخفيفة الموجودة في Accore، مع تدرج أزرق-رمادي للهيكل وأخضر فقط لحالات الإنجاز. الصور تظهر في سياقها التشغيلي لا بوصفها زينة. تؤخذ المؤشرات من بيانات حقيقية فقط ولا تستبدل ببطاقات تجميلية.

| المبدأ | تطبيقه |
|---|---|
| هرمية القرار | موجز قصير ثم قائمة عمل؛ لا أكثر من أربعة مؤشرات أولية |
| الكشف التدريجي | لا تظهر إعدادات العرض والمزامنة المتقدمة إلا في الاستوديو أو اللوحة الجانبية |
| المعاينة قبل الأثر | كل منشور أو عرض يعرض بطاقة عامة قبل النشر، مع تحذيرات الجاهزية |
| الأصل أولاً | الوسيط أصل له اسم ونوع ودور ونص بديل وحالة استعمال، وليس URL في نموذج |
| العمل المتصل | اختيار المنتج أو الحملة أو الطلب يفتح تفاصيل مرتبطة بلا انتقال ذهني بين شاشات منفصلة |
| إتاحة اللغة | تخطيط RTL حقيقي، نصوص عربية وإنجليزية، وعدم جعل رمز الحالة هو الناقل الوحيد للمعنى |

## 3. خريطة المعلومات المستهدفة

| مساحة العمل | سؤال المستخدم | المكونات الرئيسية | الإجراء الأولي |
|---|---|---|---|
| **Overview** | ما الذي يتطلب قراراً الآن؟ | نطاق زمني، 4 مؤشرات، قمع، عناصر تنتظر إجراء، صحة النشر | فتح الطلبات أو إصلاح مزامنة |
| **Order Desk** | ما وضع الطلب ومن يتابعه وماذا سيصبح؟ | فلاتر محفوظة، قائمة طلبات، تفاصيل جانبية، خط زمني، تحويل موجّه | تعيين، تأهيل، فقد، تحويل |
| **Catalog Studio** | هل المنشور جاهز للظهور العام؟ | مرشح التاجر، شبكة منشورات، مستوى جاهزية، محرر منشور، معرض وسائط، معاينة | إنشاء/تحديث/نشر المنشور |
| **Campaign Studio** | كيف سيبدو العرض ولأي منتجات ومتى؟ | قائمة حملات، مراحل باني العرض، اختيار الأهداف، نافذة زمنية، معاينة بطاقة، تدقيق التعارض | إنشاء مسودة أو نسخ حملة |
| **Operations Health** | هل تم تسليم ما نُشر؟ | حالة المزامنة، أخطاء قابلة للتنفيذ، سجل تدقيق، إعادة محاولة | إعادة محاولة الحدث أو فتح المصدر |

## 4. إدارة الوسائط والدفعات الواردة

ينشئ المستخدم أو المستورد دفعة أصول، وليس مجرد روابط. تتكون الدفعة من عناصر لها حالة `uploaded → scanned → ready → rejected`، ووسيط تخزين، واسم ملف، وأبعاد، وبدائل نصية عربية/إنجليزية، واستعمالات. لا ينتقل الأصل إلى العامة إلا بعد أن يكون `ready` ومقيداً بمنتج أو حملة عامة.

عند وصول دفعة واردات منتجات، تقارن الشاشة مفتاح المنتج التشغيلي بالمنشور: تظهر التغييرات المعلقة (صورة رئيسية جديدة، صور إضافية، تغيير عنوان أو سعر) في Review queue. يختار المستخدم: **استبدال الغلاف، إضافة للمعرض، تجاهل، أو فتح للمراجعة**. لا يحدث استبدال عام صامت للصورة، ولا يُنشر أصل جديد بدون نص بديل ومراجعة صلاحية.

## 5. باني العرض

يتكون باني العرض من خمس مراحل قصيرة: تعريف الحملة؛ اختيار المنفعة؛ اختيار المنتجات/المنشورات؛ الوسائط والمحتوى؛ الجدولة والمعاينة. تظهر بطاقة معاينة عامة ثابتة إلى جوار المراحل، وتعرض المنفعة والعنوان والصورة والنافذة وعدد المنتجات المستهدفة. تحذر المرحلة النهائية من غياب صورة أو تاجر غير متحقق أو نافذة غير صحيحة أو أهداف غير منشورة.

## 6. قرار التنفيذ

سينفذ العمل على دفعتين مترابطتين. الأولى تغير بنية المعلومات وتجربة الواجهة ضمن البيانات الموجودة، وتفصل المكونات إلى مساحة العمل والمحررات واللوحات الجانبية. الثانية تضيف نموذج أصول Marketplace ودُفعات الاستيراد وواجهات الرفع والربط، ثم تستبدل رابط الغلاف المفرد باختيار أصل متعدد الوسائط. لا توجد بيانات اصطناعية في التحليلات أو المعاينات.

## 7. مراجع التصميم والوظائف

توفر Shopify نموذجاً مفيداً للجمع بين مصادر آلية ومنتجات منتقاة داخل تجربة Collections واحدة، مع تحكم بصري في المحتوى والترتيب [1]. وتفصل إدارة الوسائط عن صفحة المنتج عبر Files قابلة للبحث حسب الاستعمال، وتتعامل مع الصور والفيديو والنماذج ثلاثية الأبعاد بوصفها محتوى عاماً فقط [2]. كما تتعامل إدارة العروض مع التعديل والنسخ والمشاركة والتعطيل كدورة حياة لحملة، لا كحقل تخفيض منعزل [3].
